# Threat model (v0.5)

What can go wrong when a lawyer shares a redacted PDF or Word (`.docx`) contract, and what this tool
does about it. "Tested" means an automated test or the seeded-leak suite (`legal-redact
bench-export`) covers it. It does not mean the route is proven closed: the suite only covers routes
we thought of.

## Assets
Personal data of natural persons inside the document (names, contact details, IDs, bank details,
dates of birth), in any place the format can hold it, and the confidential document itself while the
review page is open.

## Failure modes

| # | Failure | Example | Mitigation | Status |
|---|---|---|---|---|
| T1 | Cosmetic redaction | Black box drawn over live text | The writer deletes the content under each box; the verifier re-reads the output file with other libraries | tested (cosmetic and misaligned-box leaks caught) |
| T2 | Detector false negative | Unusual name not suggested | Human review of every page; benchmark reports misses by category; no page is ever skipped automatically | **open by nature**: 2% of synthetic documents still had a missed span; real-document rate unknown |
| T3 | Text outside the visible layer | White text, invisible text (render mode 3) | Verifier searches all extractable text with two readers; writer removes hidden text | tested |
| T4 | Text outside page content | Metadata, XMP, bookmarks, annotations, form values, attachments, JavaScript, links, thumbnails | Pre-flight refuses or flags; writer scrubs; verifier checks containers and scans every decoded object | tested |
| T5 | Text in pixels | Scans, signatures, screenshots | Pages with no usable text layer are OCR'd locally (English) and rebuilt as image-only pages with the boxes burnt into the pixel data; images on pages that DO have a text layer are still flagged for manual review. OCR cannot read handwriting, stamps, signatures or photos | tested for printed scans (clean scan passes, unredacted scan and under-covering boxes refused); **handwriting/photos unchecked by nature** |
| T6 | Leftover bytes | Old revisions, unused objects | Fresh garbage-collected file; verifier rejects extra revisions and scans raw objects | tested (incremental save caught); unused-object coverage limited to the scan |
| T7 | Verifier blind to the writer's bug | Same library writes and checks | Verifier uses pdfminer.six, pypdfium2, pikepdf; writer uses PyMuPDF | by design; shared PDF parsing bugs are possible |
| T8 | Leakage through our logs and reports | Report quotes a name | Reports, logs and decision files carry categories, page numbers, boxes and counts only | tested (canary checks on report, decisions, API state) |
| T9 | Network exfiltration | Cloud model call | No hosted model is implemented; detectors run locally. Model weights download from Hugging Face on first use | by design; first-run download is a network call by the model libraries |
| T10 | False sense of anonymity | Name removed, role plus company still identifies | Reports and README state that redaction is not anonymisation; indirect identification is a human judgment | documented only |
| T11 | Review page exposed to other software | Another web page or process calls the local API | Binds to 127.0.0.1, per-run token, Host-header check (DNS rebinding), strict CSP, no document text in API | tested (token, host, headers, no text); does not defend against other software running as the same user |
| T12 | Writer damages kept text | MuPDF shifts text after a removed word under the box | Removal starts on the preceding space; verifier warns on layout shift and on kept characters inside a box | partially fixed; line-start redactions can still shift text (warns) |
| T13 | Output path abuse | Export overwrites the source | Refuses output equal to the source; temp file then rename; file withheld when verification fails | tested |
| T14 | OCR misread | Tesseract reads "Kowalczyk" as "Kowalcyk", or drops a low-contrast name | Low-confidence words are KEPT (dropping them would hide the text that most needs review); the review page shows the original page image beside each suggestion; pre-flight states that a name OCR cannot read cannot be redacted (PF015) and every OCR page is a REVIEW finding (PF016); the decision file stores boxes, so export re-OCRs the source and searches for exactly the text the user saw | **open by nature**: a character no OCR pass reads is invisible to both detection and the export check. The control is the human comparing the page image |
| T15 | Rasterised page recoverable | A black rectangle drawn over the untouched scan, or a box too small to cover the word, leaves the original pixels in the file and in the image | The writer burns the boxes into the pixel samples before encoding and rebuilds the page from that single image; the verifier checks there is no text layer (V13), that the rebuilt page has exactly one full-page image whose box areas are dark in the extracted pixel data (V14), and that OCR of the output cannot recover a redacted string, refusing on a name fragment too (V15) | tested: vector-overlay writer, copy-without-redaction writer and under-covering boxes are all refused; clean scan passes |
| T16 | Searchability and interoperability lost | A rasterised page has no text: not searchable, not selectable, invisible to text-based downstream tools, and the file is larger than a text PDF | Pre-flight says so (PF015); README states the measured size trade-off; the verifier checks the page really has no text layer (V13) and warns if the content that should have survived is no longer readable (V16) | documented and tested; by design, a scan has to be an image if its original was one |
| T17 | OCR text leaking through our own artefacts | The recognised words end up in a report, decision file or the review API | OCR words stay in memory as needles; decision files store offsets and boxes only; reports carry categories, counts and page numbers | tested (scan decision round-trip and report checked for document text) |
| T18 | Mis-oriented scan | A sideways or upside-down page: OCR reads garbage (measured mean confidence ~30 vs ~95 upright), so nothing is redacted while the page looks reviewed | When a read looks unreliable, Tesseract OSD decides the rotation, the page is re-read upright and every box is mapped back to the original page coordinates; pre-flight runs the same OSD check on every page to be OCR'd and emits a REVIEW finding: PF017 (rotated; auto-corrected) or PF018 (orientation undeterminable; check the page yourself). No page is silently mis-read | tested: 90/180-degree scans went 0/9 -> 9/9 planted values; mutation test disables OSD and shows recall collapses; PF017/PF018 covered by tests |

## DOCX (v0.3)

The `.docx` writer edits OOXML rather than repainting a page. The routes below are the DOCX
analogue of T1-T9; each writer rule has a verifier check and a test that makes the check fail.
`docs/DOCX.md` describes what is read, refused and verified.

| # | Failure | Example | Mitigation | Status |
|---|---|---|---|---|
| T19 | Cosmetic redaction / run boundary | A name split across two `w:t` runs; a box that only looks removed | Extraction indexes every character against the `w:t` element that holds it; the writer replaces exactly those characters with U+2588 (same count, `xml:space="preserve"`) in every overlapping run; the verifier re-extracts text with ElementTree and scans every part's raw bytes for the redacted needle | tested: split-run name is gone from text and from the XML; mutation test disables run replacement and the verifier withholds the file |
| T20 | Hidden text carriers | Alternate text (`docPr descr`), tooltips, table captions, field instructions (`w:instrText`, `w:fldSimple w:instr`), hyperlink `mailto:` targets, content-control alias/tag, inline custom-XML attributes, bookmark names | Pre-flight counts them and emits REVIEW PF111 (they are not body text, so the detectors never see them); the writer removes them (hyperlinks unwrap to plain text, external relationships are dropped, bookmark names are replaced); the verifier fails V104 if any survives | tested: every carrier above is planted, then absent from the output; unit test + CLI end-to-end |
| T21 | Comments | Comment text and comment author names are personal data and are not in the page body | Pre-flight REVIEW PF112; the writer removes `word/comments*.xml`, `word/people.xml`, comment range marks and references and their relationships/content types; the verifier checks no comment part or mark survives | tested: comments stripped after acknowledgement; mutation test keeps the comment part and the verifier withholds the file |
| T22 | Tracked changes | Deleted text (`w:delText`) and revisions can hide the original wording | Pre-flight REFUSE PF105 on insertion/deletion/move/format-change elements. The tool never resolves revisions; the lawyer accepts/rejects them in Word first | tested |
| T23 | Metadata | `docProps/core.xml` (creator, editor, title), `app.xml` (company, manager), `custom.xml`, `people.xml`, page thumbnails, document variables, mail-merge/attached-template settings | Pre-flight INFO PF116/PF117; the writer rebuilds core/app as empty property parts (no value, child element name or attribute survives), drops custom properties, people, thumbnails and document variables, removes mail-merge/template settings; the verifier fails V105 if any value, child or attribute is non-empty, or any of those parts survives | tested: metadata scrubbed; mutation test disables the scrub and the verifier withholds the file |
| T24 | Embedded objects, macros and unknown parts | `vbaProject.bin`, `word/embeddings/*`, ActiveX, `altChunk`, subdocuments, charts/SmartArt, an image/font file with an unrecognised extension, legacy form fields | Pre-flight REFUSE: PF103 macros, PF106 embedded objects, PF107 parts outside the recognised set (including image/font extensions outside the allowlist), PF119 `altChunk`/subdocuments, PF122 legacy form data. No unknown part is ever copied to the output; the writer re-checks and refuses rather than guesses. (AutoText/glossary is a recognised text part and is read + redacted.) | tested (one case per code) |
| T25 | Text outside the supported containers | A `w:t` directly under the body, text in an XML comment / processing instruction / DOCTYPE / CDATA outside a text part, a name hidden in content-type or relationship attributes, numeric text hidden in an unknown element inside a drawing | Extraction enforces a coverage invariant: every text node must be in a `w:t` the writer can rewrite, in a field-instruction element the writer removes, or be numeric text in one explicitly allowlisted drawing-layout element (`wp:posOffset` under `wp:positionH`/`positionV`, `wp14:pctWidth`/`pctHeight` under `wp14:sizeRelH`/`sizeRelV`, plausible range only). Everything else is refused (PF108/PF121). Relationship/content-type attributes must match the format's structural vocabulary | tested: each construct refused with its code; anchored/floating drawings with real `wp:posOffset` values are accepted and export |
| T26 | Text in pixels / images | Screenshots, signature images, logos, pasted scans | When an OCR engine is available, each image is decoded and read into its own text container (at a 300-dpi geometry convention), so text inside it can be suggested, redacted in the pixels and re-checked. Multi-frame containers (animated GIF, APNG, animated WebP, multi-page TIFF) are detected from the raw bytes **before** decode and REFUSED (PF127), so no unread frame can survive; a single-frame GIF is normalised to PNG. An image with no words from the engine is REFUSED when large/content-bearing (PF132) and needs an explicit acknowledgement when small (PF131); an image with very small text or a low effective resolution is a REVIEW (PF133); engine word boxes that lack contrast in the source pixels refuse the file (PF128). Every export report carries a WARN V112 naming any image whose text was never read **or was too small to read reliably**. With no engine or with `--no-ocr`, an image covering at least 25% of a page is REFUSED (PF123) and smaller images are REVIEW PF113. Every image is re-encoded metadata-free PNG and checked by V109-V112 | tested: image OCR path end-to-end with a planted-text image (pixels black, original bytes gone, V109-V111 pass); multi-frame/malformed probes refused; no-burn/leftover-metadata mutations withheld; zero-word/large, zero-word/small, tiny-text, low-res, low-contrast and dishonest-engine probes; V112 WARN for unread and PF133 tiny-text images; **open by nature**: what OCR cannot read is not redacted — large unread images are refused, small/tiny ones are an explicit human acknowledgement plus a WARN in the report |
| T27 | Writer damages the document | A `.docx` that no longer opens, or content silently dropped | The writer preserves ZIP entry order/compression, copies every part it does not edit byte-for-byte, keeps paragraph and run counts, renames bookmarks instead of dropping them, and removes only the carriers it reports; the verifier checks byte-identity of untouched parts, paragraph/run counts, content types and relationship targets (V106/V107). Removed by design and reported: comments, links (plain text), field instructions, custom XML | tested: python-docx can open the output; integrity checks fail when a part is misplaced |
| T28 | Leakage through our own reports | A report or decision file quotes a name | Findings and reports carry counts, codes and structural labels only; decision files store container numbers and offsets, never text | tested (canary checks on report, decision file and CLI output) |
| T29 | Package metadata made of text | A person's name as an image filename (`word/media/Ivanova_passport_...png`), a card number or person name as an embedded-font family name in `word/fontTable.xml`, a name as a style name or list-numbering format string | Image and embedded-font parts are renamed to generated neutral names on export, with relationships and content types updated; the verifier fails V106/V108 if a source-chosen name survives. Part names and presentation-only names are scanned with the structured-identifier rules and the file is REFUSED (PF124) if one reads like an e-mail/ID/IBAN/card. Style/font/list-numbering names that look like a *person* rather than an identifier are copied verbatim and reported by PF126 (INFO) — renaming style or font definitions would change the document's appearance | tested: media/font names renamed and verified; identifier-shaped names refused; person-shaped presentation names disclosed (documented limit) |
| T30 | Unicode normalisation | A name written in decomposed form (NFD: base letter + combining mark), zero-width characters or full-width forms | The detectors see the extracted code points; the PDF verifier's normalisation (NFKC, casefold, whitespace collapse) covers full-width and compatibility forms, and the DOCX verifier checks needles the same way. **NFD is a detection-level gap not compensated here**: the extracted offsets must map to runs, so the DOCX extractor is not normalised (doing so would break redaction geometry). Documented as a known limitation and future detection work; affects PDF identically | **open**: a decomposed name can be missed by detection and therefore not redacted; documented in README and docs/DOCX.md |

| T31 | Malicious or buggy custom OCR engine | A wrapper returns boxes outside the page, overlapping nonsense, missing words, fabricated words, or crashes halfway | Every command-engine answer is strictly validated (JSON object, word array, finite boxes inside a 0..1 top-left page frame with 0 <= x0 < x1 <= 1, confidence 0..1, non-empty text, caps on words/payload, required boolean `local`, exit 0, timeout); anything invalid is a refused page, never "no text". Omitted words reduce what can be suggested (pre-flight says so: PF015/PF016); the verifier checks the redactions that were made, and its V15 output OCR is Tesseract-preferring. A wrapper is code the user chose to run and receives the page image by design | tested: invalid JSON, out-of-bounds box, bad confidence, empty word, missing `local`, locality contradiction, crash, timeout, oversized/violating payloads all refused; a same-engine leak is still FAIL |
| T32 | Cloud/third-party OCR confidentiality | The configured engine sends page images to an external service: third-party access, retention/logging, data location and onward transfers, interception or a provider breach | Two gates: (1) a non-local engine is refused before any page is rendered unless `--allow-cloud-ocr` (or `LEGAL_REDACT_ALLOW_CLOUD_OCR=1`) approves the run -- proven by a marker test that the wrapper is never invoked; (2) pre-flight REVIEW PF019 carries the verbatim disclaimer and export stays blocked until acknowledged (CLI `--ack PF019`; review page shows a warning banner and an explicit approval checkbox, not the generic acknowledgement). Decision files pin locality; a cloud-pinned file needs approval again on the exporting invocation. The local Tesseract default does not carry this risk | tested: no-approval run exits 2 before OCR with no engine invocation; approved run prints the disclaimer and requires the ack; review page state carries the warning and label; cloud decision file needs approval on export |
| T33 | Suggest/export engine mismatch | The decision file was made with one reader and the export runs with another (or an old file has no engine record), so boxes and needle text describe different readings | Suggest records `ocr {engine, version, local, cloud}` in the decision file. Load/export refuse with a re-run-suggest message (PF022 REFUSE, no output) when the current spec or declared locality differs, or when a document with OCR pages has no pin at all. Version is recorded for diagnostics; identity is the engine spec | tested: recorded-engine change refused with no output; old file without the pin refused; direct exports checked, not only the CLI |
| T34 | Circular verification | A custom engine checks its own output, so a systematic error passes unchecked | V15 prefers Tesseract as the output reader whenever Tesseract exists, even when a custom engine produced the suggestions (independent cross-check). Without Tesseract the configured engine is the only reader; the check is labelled `SAME-ENGINE (weaker)` in the report and detail, pre-flight REVIEW PF021 requires an acknowledgement, and failures are still FAIL -- never converted to PASS | tested: Tesseract-preferred label when it exists; same-engine label and mandatory PF021 without it; a writer that removes nothing still fails V14/V15 under same-engine checking |
| T35 | Orientation unknown with a custom engine | A rotated page is read by a custom engine with no orientation handling; words come back in the wrong frame or are misread | With Tesseract installed, its OSD orientation check still runs in pre-flight regardless of the configured engine (PF017/PF018 REPORT/an auto-corrected rotation). Without Tesseract the pipeline cannot machine-check orientation: PF023 REVIEW requires the lawyer to check the page images, and the command contract requires boxes already mapped to the upright page frame | tested: PF017 with patched OSD when Tesseract exists; PF023 when it is missing; the reviewed contract documents the wrapper's responsibility |
| T36 | Command injection / runaway wrapper | A malicious or broken wrapper string executes shell syntax, hangs, floods stdout, or leaks document text into an error message | The command is split into argv and executed directly (no shell, no expansion; quoted arguments supported); stdout is written to a size-capped temp file and parsed, stderr is discarded and never copied into a report or error; a 180 s timeout and exit-code check refuse a hung/crashed wrapper; validation errors name fields and counts, never recognised text | tested: timeout/crash refusal, invalid output never echoes document text, payload/word caps, no-shell split of quoted paths |

## DOCX review page (v0.5)

The review page can show a rendered view of a `.docx` (through Word or LibreOffice) with mapped
boxes. The writer/verifier remain the source of truth; the render is display only. New threats:

| # | Failure | Example | Mitigation | Status |
|---|---|---|---|---|
| T37 | Box at the wrong text (misleading review) | A suggestion box drawn over a different occurrence; a duplicate matched twice; a manual box mapped to the wrong passage | Alignment is token-level, monotone and per .docx container (headers/footers/notes/text boxes are separate containers because the rendered order differs), with anchors and a neighbour-context requirement. Rendered mode is used only if ≥90% of the .docx text aligns and **every** suggestion maps cleanly; otherwise the page switches to text review and says why. Two suggestions mapping to the same rendered text, a span without aligned context, or an unreliable mapping are never drawn. Manual boxes must fully contain whole words, be contiguous in one container and map forward again, otherwise they are rejected with a message. Export always re-derives needles from the decision's character offsets and the V101-V108 verifier checks the .docx, never the rendered PDF | tested: alignment fixture (mapping, word identity, reverse round-trip), partial/empty/unmapped/isolated rejections, rendered + text HTTP round-trips; mode-level fallback tests |
| T38 | Renderer is an external, attackable program | A compromised Word/LibreOffice install, a document that makes the renderer fetch linked remote content, macros or OLE actions while rendering | Rendering is optional and detected, never installed; the renderer is the user's own office program. Word is opened invisible/read-only with macros force-disabled (`AutomationSecurity`) and link updates off, and is closed/quit after use (a PID sweep kills only the Word instance this render started; an attached pre-existing Word is not quit). LibreOffice runs headless with a throwaway profile. The renderer's output is used for display only and never becomes the exported file; no Python dependency is added; a render failure degrades to text review | by design; documented. **Open by nature**: a renderer may still resolve externally-linked content the source document references — keep the renderer offline if that matters. Word path exercised end-to-end; LibreOffice path implemented/unit-tested but not exercised on a machine with LibreOffice installed |
| T39 | Temporary rendered PDF exposure | The unredacted document sits in a temporary PDF while the review page is open | The render is written to a unique temporary directory (not the output folder), deleted when the session ends or the render fails; the path is not logged and nothing of the render reaches reports or decision files | documented; same-user processes could read it while open, and a crash may leave it for OS temp cleanup — inherent to rendering |
| T40 | Document text exposed through the review API | Text review needs context excerpts; a page serving them could be read by other local software | Text-mode excerpts exist only in memory and are returned to the local page over the token-authenticated 127.0.0.1 server (per-run token, Host check, CSP, no-store); they are never written to decisions, reports or logs. Rendered mode returns page images and boxes but no document text. Decision files remain text-free | tested (API state text-free in rendered mode; decisions text-free in both modes; existing local-only security tests cover the server) |

## DOCX images (v0.5)

Embedded images are decoded, read with the configured OCR engine, redacted in their pixels and
re-verified. The original bytes are never written to the output. New threats:

| # | Failure | Example | Mitigation | Status |
|---|---|---|---|---|
| T41 | OCR misses text inside an image | A fuzzy, rotated, low-contrast or tiny-text image, handwriting, a stamp, a photographed card, or a weak/dishonest custom engine: text is not read, so the detectors cannot flag it | The image is read with the same validated engine abstraction as scanned pages. If the engine finds no words: large/content-bearing images are REFUSED (PF132) and small ones need an explicit acknowledgement (PF131: "pixels were NOT checked ... personal data may survive"); an image with very small OCR word boxes or a low effective resolution is a REVIEW (PF133) even when some words were returned, and PF133's tiny-text condition is the same one used for the export disclosure; word boxes with no contrast in the source pixels refuse the file (PF128 — contrast/variance evidence, independent of the engine, so valid low-contrast glyphs pass). **Every export report carries a WARN V112 naming each image that was not fully verified: text never read, OCR not used, or text too small to read reliably (PF133)** — with per-image wording and the same row in the evidence report — so the PASS line is visibly qualified; every accepted image passage is re-read in the output (V110, all images) and export re-reads every source image so an accepted passage readable in another image withholds the file. A misread character is still invisible (stated in PF113 and the report limits); handwriting/signatures/stamps/photographs are listed as not understood | **open by nature** (same as PDF OCR) for what OCR cannot read at all: large cases are refused, small/tiny/low-res cases are explicit human acknowledgements plus a WARN in the report, and accepted text is always verified in the pixels; the tool never claims the unread/unverified pixels were checked |
| T42 | Image metadata | EXIF GPS/device data, XMP packets, ICC profile, DPI/text chunks in the image file (including images with no text to redact) | **Every** image in an export is re-created from raw samples and re-encoded as lossless PNG with all non-critical chunks stripped — not only images with accepted spans. Untouched images are therefore pixel-identical but their metadata is gone. V111 scans every output image for EXIF/XMP/ICC/DPI/text markers | tested: untouched metadata-only image (audit I03) and PNG tEXt/pHYs fixtures exported without markers and with pixel equality; mutation that leaves EXIF in an image is withheld |
| T43 | Re-encoding damage or decompression mismatch | An image is blurry, resized, colour-shifted, or an original file survives elsewhere in the package | The burn and re-encode work on the decoded native-size RGB pixmap, preserve the exact pixel dimensions, flatten transparency to white and encode lossless PNG; the verifier re-decodes every image, checks dimensions and that untouched images are pixel-identical (V109) and that no original image byte sequence survives in any part (V111) | tested: dimension/black-area/pixel-equality checks; a writer that keeps the original bytes is refused; an untouched image must decode to exactly the same pixels |
| T44 | Image redaction exposes a different leak | The pixels are black but the original bytes/metadata survive, or a different image is matched as the redacted one (two same-size images) | The writer renames image parts canonically (sorted source order -> `word/media/redacted_N.png`) and the verifier rebuilds that exact pairing from the source package instead of guessing by pixel dimensions, failing closed on a count/name/tamper mismatch; it searches every output part for original image bytes (V111); every source image part is renamed neutrally and content types are updated (V106/V108) | tested: two same-size redacted images export PASS with the correct per-image pairing; an image-count tamper fails V109; original-byte mutation withheld; package integrity re-checked (V107) |

## Out of scope for v0.5
Non-English OCR; handwriting and signature detection; photographs/stamps; text rendered as vector
outlines; animated or multi-page image files (refused); digital
signatures (redaction invalidates them); `.docm`/macro-enabled and encrypted files; legacy `.doc`
(refused, convert first); tracked changes (refused, resolve in Word first); `.docx` embeds of
charts/SmartArt/OLE (refused); precise removal of text hidden in style names, embedded-font family
names, list-numbering format text or unusual theme/settings values (copied verbatim, reported by
PF126; identifier-shaped values refuse the file); decomposed-Unicode (NFD) evasion of detection; a
guarantee that Word and LibreOffice lay out every construct identically (rendering is display only;
any construct that cannot be aligned falls back to text review); review of files the pre-flight
refuses (fix them in Word first — the review page shows the findings, not a rendered document); a
guarantee that an OCR engine reads every glyph in an image (the pre-flight disclosures and the
output re-OCR are the controls); a
legal conclusion that a document is anonymous or GDPR-compliant.

## Refuse vs review
- **Refuse** (export blocked, PDF): encrypted, no extractable text when OCR is unavailable or
  disabled (`--no-ocr`), embedded files, XFA forms.
- **Refuse** (export blocked, DOCX): encrypted container, legacy `.doc`, `.docm`/`.dotx`, macros or
  ActiveX, tracked changes, embedded OLE/package objects, `altChunk`/subdocuments, legacy form data,
  unknown parts, text outside the supported containers, malformed packages, text-carrying XML
  constructs, images covering ≥25% of a page only when no OCR engine is used (PF123), a
  multi-frame container detected from its bytes (PF127: animated GIF/APNG/WebP, multi-page TIFF), an
  unreadable/unsupported/oversized image (PF127), an engine failure or engine word boxes with no ink
  evidence (PF128), an unread large/content-bearing image (PF132), and part/presentation names that
  read like a structured personal identifier (PF124).
- **Review** (lawyer must acknowledge, PDF): OCR use (PF003/PF004), what OCR cannot see (PF016),
  rotated scans it will correct (PF017), scans whose orientation could not be determined (PF018),
  cloud/third-party OCR (PF019, the confidentiality disclaimer), no independent cross-check because
  Tesseract is missing (PF021), orientation uncheckable without Tesseract (PF023), images on text
  pages, annotations, form fields, JavaScript, layers, bookmarks.
- **Refuse** (export blocked, PDF, OCR engine): a configured engine that is unavailable or invalid,
  or a non-local engine without run approval (PF020); a decision file whose pinned engine or
  locality no longer matches this run, or that has no pin while the document has OCR pages (PF022,
  re-run suggest).
- **Review** (lawyer must acknowledge, DOCX): hidden-text carriers being removed (PF111), comments
  being removed (PF112), image OCR use and what it may miss (PF113), an unread small image (PF131,
  with an explicit "pixels were NOT checked" disclosure), an image whose text is very small or
  displayed below ~150 dpi (PF133), custom XML being removed (PF114), a same-engine output image
  check because Tesseract is absent (PF130), and cloud OCR of embedded images (PF019, the
  confidentiality disclaimer).
- **Warn** (report and evidence report, no withholding, DOCX): V112 names every exported image that
  was not fully verified — text never read, OCR not used, or PF133 tiny-text images whose pixels were
  not verified for hidden text — so a PASS never looks like a certification of those pixels.
- **Info** (no decision needed, DOCX): what was read (PF118), metadata that will be scrubbed
  (PF116/PF117), presentation-only text that is copied verbatim (PF126), image OCR counts and
  rotation reports (PF129), and that every image will be re-encoded metadata-free PNG.
- **Review page mode** (DOCX, no export decision): rendered when a renderer is available and the
  alignment is trustworthy for every suggestion, text review otherwise. The mode never changes what
  export writes or verifies; a text-mode export is exactly as fail-closed as a rendered-mode one.
